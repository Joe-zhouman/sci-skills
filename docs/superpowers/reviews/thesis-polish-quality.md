## Issues

### Critical (Must Fix)

1. **`scripts/parse_paperyy.py:75-79` — a legitimately clean PaperYY report is misreported as format drift.** A report whose sentences are all `em.low` (zero `high`) yields `rows == []`, which `main()` reports as "未解析出任何高度疑似句（空报告/格式漂移……需更新 parser）" with rc 1. Confirmed by execution: `<p class='uncheck'>第一章</p><em class='low' id='1'>低风险句。</em>` → 0 rows → structured error. This is a real state (a thesis re-detected after one polish round can be clean), it produces a *wrong verdict class* on valid input, the message actively misleads ("需更新 parser"), and it breaks the manifest contract consistency the two parsers are supposed to share — parse_paperpass.py:83-87 (F6) implements exactly this distinction and paperyy doesn't. Note the sibling's reasoning explains why it *can*: paperpass has structural sentinels; paperyy has them too but doesn't use them. → Fix: in `parse()`, also count total `em` sentences seen (high+low) and whether any `p.uncheck` section matched; if structure was seen but highs == 0 → return a clean marker so `main()` prints the 0-sentence manifest with rc 0 (mirroring parse_paperpass.py:86); only a report with *no em/p structure at all* is drift. Add the low-only test (currently no test covers it — the only zero-case test, test_parse_paperyy.py:73-81, uses a report with no `em` at all, which is why the bug survived) and update tests/README.md:109-111.

2. **`scripts/parse_paperyy.py:26` — `_TAG_RE` is quadratic on unclosed tags; a drifted/hostile report hangs the parser instead of producing the promised drift error.** `<(em|p)\b([^>]*)>(.*?)</\1>` — every `<em…`/`<p…` start with no matching closer makes the lazy `(.*?)` scan to end-of-document. HTML5-legal unclosed `<p>` is a plausible drift shape, and SKILL.md rule 8 (:115-118) declares reports an UNTRUSTED surface, so input shape is adversarially choosable. Measured: 50KB/2000 unclosed `<em>` → 1.10s; 125KB → 6.89s; 250KB → 27.62s (clean quadratic; a 1MB report ≈ minutes, 2MB ≈ half an hour — the full-size run did not finish in 120s). Well-formed reports are linear and fast; the damage lands precisely on the drift path the design promises to catch as a clean rc 1. → Fix: pre-tokenize (`re.split(r"(<[^>]*>)", html)` and walk tags linearly), or bound the inner scan so it can't run past the next tag open. Confirm against one real PaperYY report after the fix.

### Important (Should Fix)

3. **`scripts/parse_paperpass.py:59-61` — hostile JSON shapes crash with a traceback, violating the file's own structured-error posture.** The `isinstance(o, dict)` guard at :59 protects one layer but not the next: (a) `originalFragmentInfo` a *string* → `fi.get` at :60 raises AttributeError; (b) `sectionContentList` containing a non-string → `"".join(...)` at :61 raises TypeError. Both confirmed by execution (`json.dumps` of exactly those shapes → AttributeError / TypeError out of `parse()`, uncaught in `main()`). The docstring (:11) promises "报告内容 UNTRUSTED——纯文本解析不执行" with structured errors as the failure mode; a traceback is not one. → Fix: `if not isinstance(fi, dict): continue` after :59, and `"".join(str(x) for x in fi.get("sectionContentList", []) or [])` at :61. Two tests pin the shapes.
4. **`scripts/parse_paperyy.py:47` — inner tag-strip lacks `re.S` while `_TAG_RE` uses it, so multi-line nested tags leak into the sentence.** `_TAG_RE` is compiled `re.S` (:26) so `inner` may contain newlines, but `re.sub(r"<.*?>", "", inner)` is not DOTALL — a tag spanning a newline survives whole. Confirmed: input `<em class='high' id='1'>前<span\nclass='x'>中</span>后。</em>` → sentence `"前<span\nclass='x'>中后。"`. The manifest's whole job is text the agent aligns to current tex (SKILL.md Stage A "Align", :234-237); embedded markup degrades that match. (parse_paperpass is unaffected: its `\n` are stripped at :61 before the strip at :62.) → Fix: `re.sub(r"<.*?>", "", inner, flags=re.S)`.
5. **`scripts/check_polish.py:186-190` — N+1 read pattern: every tex file is re-read and re-comment-stripped once *per ledger pair*.** The `for v, canon in pairs:` loop contains `tf.read_text(...)` + `splitlines()`, so cost is O(pairs × files) full decodes and O(pairs × lines) `_strip_comment` calls — with a 50-pair ledger and 15 chapters that's 750 full-file reads where 15 suffice. Check 2 already does it right (single pass collecting labels and refs, :202-214). → Fix: read each file once into `{path: (name, lines)}` before the pair loop, then scan pairs against the cached lines.
6. **`scripts/check_polish.py:217` — the `\ref{key}` echo bypasses the file's own sanitize discipline.** `_sanitize` exists (:49-52) with an explicit rationale ("原始 ledger/报告值不可直接进输出，防终端 title 改写/日志行伪造") and is applied to the ledger echo at :196-197 — but `key`, captured by `[^}]+` (:149) from raw tex bytes, is interpolated raw. A tex file containing `\ref{<ESC>]0;title<BEL>}` echoes the escape into the issue line. Same surface the B5 lineage hardened everywhere else. → Fix: `f"✗ {fname}:{ln} \\ref{{{_sanitize(key)}}} 悬空——\\label{{{_sanitize(key)}}} …"`. (`test_ansi_stripped_from_issues` covers only the ledger side; add the tex-side key.)
7. **`scripts/check_polish.py:220-224 + :233` — the truncation header contradicts its own sentinel line.** `check()` returns `kept` (MAX_ISSUES + sentinel), and `main()` prints that length as the issue count. Measured with 260 real issues: header says `check_polish: 201 个一致性问题`, the last line says `另有 60 个 issue 截断（共 260）` — same output, two different totals, and the sentinel is counted as an issue. `test_truncation_cap` (:250-258) pins only `check()`'s return shape, so `main()`'s count is untested. → Fix: return `(kept, total)` from `check()` (or have `main()` subtract the sentinel and print the true total), and pin the header in a test.
